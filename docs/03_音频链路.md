# 音频链路：按五段检查

| 段 | 检查对象 | 常见问题 |
|---|---|---|
| 进程 | call_loop 心跳和进程日志 | 进程已退出却仍能接通 QQ 电话 |
| 耳朵 | QQ 实际播放端点与心跳记录的监听端点 | 只看默认扬声器会误判；应用会单独选输出 |
| 嘴 | TTS 返回音频并进入虚拟线 | 服务存在但模型错误、参考文字不匹配、输出设备错 |
| 回程 | QQ 使用虚拟录音端点 | 本地能听见不代表对方听得见 |
| 设备 | 播放和录音端点列表 | 中英文设备名、多个虚拟线、独占占用 |

```text
QQ 来声 → 播放端点 → WASAPI 环回 → ASR → 模型 → TTS
TTS → audio.playback_hint → 虚拟线 → audio.capture_hint → QQ 麦克风 → 对方
```

`audio_doctor.py --json` 会发出短试音，须在准备好的通话中运行。
没有活跃 QQ 音频会话、没有有效心跳或跳过试音时，不能视作全链路通过。
`mic_guard.py` 会改变系统默认麦克风；默认关闭。启用前记录原设备，停用后根据需要恢复。

第一次接通后，在 QQ 通话窗口把鼠标移到麦克风旁，点击出现的小箭头：

- 麦克风选 **CABLE Output (VB-Audio Virtual Cable)**，用于把合成声音送给对方。
- 扬声器选电脑实际播放声音的端点，例如 **扬声器 (Realtek(R) Audio)**；它必须与通话监听日志的端点一致。
- Windows 音量不要静音，QQ 在音量混合器中也应有音量。日志中的输入峰值一直为零时，先检查这一路。

每次新通话以及 QQ 或 Windows 重启后，都要确认该菜单的勾选项。第二台设备实测：即使 QQ 没有重启，新通话的麦克风也可能恢复为系统默认的物理麦克风。此时识别、生成回复和本机音频写入可以全部正常，但对方仍听不到声音。验收必须包含挂断后重新拨打，并在不手动切设备的情况下确认回复。
配置中的 `audio.capture_hint` 供项目选择与检查设备使用，不会替你修改 QQ 的设备选择。

如果 QQ 在新通话恢复默认设备，可在 Windows「设置 → 系统 → 声音 → 音量合成器」展开 QQ，将该应用的输入设备指定为 **CABLE Output**。这项设置仍须通过挂断重拨验证，不能以保存成功代替实测。不要把 QQ 输出设备也选成 CABLE Input，否则会改变来声监听链路。

播放统计中的“首段写入”指第一段音频写入本机输出设备，不等于对方听到声音的端到端延迟。
出现“未播放”或“语音播放失败”时，该轮不能算回复成功；监听会继续，具体原因应结合 TTS 日志检查。

源环境 VAD 的关键设置保留在 call_loop：0.9 秒结束静音、0.45 秒预录、打断持续阈值与起声保护。
这些是算法参数，不保证所有麦克风、网络和噪声条件下达到同样指标。
