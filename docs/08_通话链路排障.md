## 通话链路：把这次踩到的坑补进排查文档

这份文档是在真实设备上把「语音通话 / 视频通话」跑通后回填的经验，按现象组织，
不依赖我本地的具体音色或 TTS 实现。都是**可复现的确定性故障**，不是玄学。

---

### 1. 通话里「她声音像很粗的男人」= 裸 PCM 采样率对不上

`call_loop` 的流式播放约定是：

```python
TTS_RAW_RATE = int(setting("audio.tts_raw_rate", 32000))
...
data, sr = payload, TTS_RAW_RATE     # 收到的裸 PCM 一律按 32000 解释
```

如果 TTS 侧按 **48kHz** 回裸 PCM，会被当成 32kHz → 重采样补到 1.5 倍长度 → 按 48kHz 播放，
结果是**时长 ×1.5、音高 ÷1.5**，听感就是「低沉、很粗的男人声音」。

同一句音频走 `media_type=wav` 时一切正常，所以特别容易误判成「音色模型退化」。

排查：让 TTS 侧同时回 wav 和 raw，比较时长与基频：

```
wav 24000Hz  3.09s  f0≈400Hz
raw  3.09s   f0≈400Hz     ← 合格
raw  2.06s   f0≈286Hz     ← 说明 raw 按 48k 发出、被当成 32k 播了
```

修法（二选一）：

- TTS 侧按 `audio.tts_raw_rate` 输出裸 PCM；或
- 把 `audio.tts_raw_rate` 改成 TTS 侧真实采样率，并确认播放端不二次重采样。

### 2. 流式 ASR 偶尔卡 40 秒，导致「她一直不吭声」

DashScope 的流式识别（`paraformer-realtime-v2`，WebSocket）在网络抖动时会
**建连超时 5s、`stop()` 挂住几十秒**，期间通话循环完全阻塞。日志表现：

```
（首段写入 55.6s ＝ 识别 44.2 + 思考 1.9 + 合成）
```

修法：给识别加**硬超时**，并准备一条不依赖网络的兜底。关键是超时实现不能写成

```python
with ThreadPoolExecutor() as pool:      # 退出时 wait=True，会等卡住的线程 → 超时无效
    pool.submit(...).result(timeout=4)
```

正确写法：

```python
pool = ThreadPoolExecutor(max_workers=1)
try:
    return pool.submit(fn).result(timeout=4)
except TimeoutError:
    return ""
finally:
    pool.shutdown(wait=False)          # 关键：不等待卡住的线程
```

推荐兜底顺序（实测延迟）：本地 faster-whisper（0.6s）→ 云端文件级 OCR/ASR（1.7s）→ 流式（最后）。
云端文件级识别用 `qwen3-asr-flash`，吃本地 wav 文件、还返回语言与情绪标注：

```python
MultiModalConversation.call(
    model="qwen3-asr-flash",
    messages=[{"role": "user", "content": [{"audio": "file:///C:/path/fail.wav"}]}])
```

另外建议把识别失败的音频**落盘留证**（`data/asr_fail/*.wav`），否则无从判断是
「音量太小」「录到的是音乐」还是「模型挂了」。实测两种典型样本：

- 3.4s、峰值 0.6、RPM 无语音段落 —— 本地 whisper 与云端都返回空，音频分析显示是**音乐**；
- 2.5s、峰值 0.01 —— 太轻，归一化后仍识别不出。

### 3. 电脑静音 → 她「聋了」

她「听」你，靠的是把 QQ 播放端的声音**环回录音**。所以：

- 静音或把「扬声器」音量调到 0 → 环回是静音 → ASR 恒为空；
- 想安静只能降低音量（实测 25–35% 环回仍有余量），**不能静音**；
- 手机连蓝牙耳机不影响这条链路，它只影响你自己听/说。

建议在保活脚本里做一次**音量自检**（`pycaw` 读 endpoint 的 mute/volume，
发现被改就拉回已知良好值），实测用户手调音量后确实会忘记改回来。

### 4. 视频通话自动接听后摄像头没打开

`call_agent` 里按按钮文本点「开启视频」，但 QQ 不同版本文案是
「开启视频 / 开启摄像头 / 打开摄像头」，甚至可能只有图标无文字（`window_text() == ""`）。
建议：

- 匹配放宽为「包含 视频/摄像 且不含 接听/挂断/关闭/语音」；
- 找不到时把窗口里所有 Button 的 `window_text()` 与 `automation_id()` 打进日志，
  下次直接按实际名字点；
- 若 `descendants(control_type="Button")` 抛 COMError，退化为全量 `descendants()` 再过滤。

### 5. 保活 / 自启（部署侧）

长时间挂机的常见故障是「某个进程悄悄死了」而不是配置错。建议：

- 一个幂等的 `keepalive` 脚本，每 2 分钟检查端口/进程，缺什么补什么（用互斥文件防并发）；
- 登录自启放「启动」文件夹即可，不需要管理员权限；
- 关键端口：TTS（9880）、AstrBot（6185/6199）、PMHQ（13000）、LLBot 的 node 进程；
- 日志只在真的动手时写一行，否则天天翻日志没法看。

---

以上都只是「让通话链路稳定可用」的工程修补，不改变 QQ 视频画面仍未通过验收这个结论
（见上文「QQ 仍用实体镜头」一节）。

### 6. 把本地 ASR 放到 GPU 上：延迟从 1.9s 降到 0.27s

本机环境：RTX 5060 Laptop（8GB）+ `torch 2.9.1+cu128`（已在 `.venv-tts` 里）+ `ctranslate2 4.8.3`。

**关键不是换模型，而是让 ctranslate2 找到 cuDNN/cuBLAS**：它从 PATH 加载这些 DLL，
而 torch 的 `lib` 目录里本来就带着 cuDNN 9：

```python
import os, torch
lib = os.path.join(os.path.dirname(torch.__file__), "lib")
os.add_dll_directory(lib)
os.environ["PATH"] = lib + os.pathsep + os.environ["PATH"]
from faster_whisper import WhisperModel
model = WhisperModel("medium", device="cuda", compute_type="float16")
```

实测（同一段 4.3 秒中文语音、热身之后）：

| 配置 | 延迟 | 识别结果（标准答案：海洋，你今天话有点少，是不是累了？） |
|---|---|---|
| CPU int8 · small | 1.9s | 海洋,你今天**画**有点少,是不是累了? |
| GPU float16 · small | 0.11s | 海洋,你今天**画**有点少。 |
| **GPU float16 · medium** | **0.27s** | 海洋,你今天**话**有点少,是不是累了? ✅ |

结论：**GPU 让「大模型」比原来的「小模型 + CPU」还快 7 倍，同时把同音错字修掉了。**
显存占用：medium float16 约 1.5GB；与本地 GPT-SoVITS 备份同时常驻约 3.9GB / 8GB。

工程上要注意的两点：

1. **首次加载慢**：CUDA 初始化 + 模型加载约 40~60 秒（之后每句 0.27s）。
   启动脚本应把它和通话循环解耦——识别服务没就绪时，通话侧自动退回云端识别，
   等本地服务起来了自然接管，不要因为"没就绪"让整条链路失败。
2. **CPU 回退用 small，不要用 medium**：GPU 不可用时 medium 在 CPU 上要 4~6 秒，
   反而比 small（1.9s）差。建议模型参数与设备解耦，例如
   `--model medium --device cuda --cpu-model small`。
